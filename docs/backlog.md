# Backlog agents-farm

Рішення, які визначають обсяг (відповіді на уточнювальні питання):

| Питання | Рішення |
|---|---|
| Де відкривати нову / відновлену сесію | **У цьому ж терміналі**: TUI призупиняється (`App.suspend()`), `claude` займає екран, після виходу повертаємось у TUI |
| Якими сесіями керуємо | **І Desktop, і CLI**: поведінка залежить від поля `entrypoint` |
| Джерело лімітів | **statusLine** (офіційний канал `rate_limits`) |
| Відсоток по сесіях | **Обидва показники**: заповнення контексту і частка в лімітах |

Оцінки: **S** ≤ пів дня · **M** 1–2 дні · **L** 3+ днів.

---

## Що показало дослідження (на цій машині, Claude Code 2.1.319 / 2.1.325)

Ці факти змінюють план, тому вони вгорі.

1. **`~/.claude/sessions/<pid>.json` — готовий реєстр живих процесів.** Поля: `pid`, `sessionId`, `cwd`, `name`, `status` (`idle` / `busy`), `entrypoint` (`claude-desktop` | CLI), `kind`, `version`, `startedAt` (мс), `procStart`, `updatedAt`, `statusUpdatedAt`, `messagingSocketPath`. Усі 4 живі сесії тут мають `entrypoint=claude-desktop`. Це відкриває PID, kill і живий статус без вгадування з транскриптів.
2. **`procStart` у UTC, а `ps -o lstart` показує локальний час** (різниця 2 год). Для захисту від перевикористання PID порівнювати `startedAt` (epoch мс), а не рядки.
3. **Структура лімітів на Pro: 5-годинне вікно + тижневе (all models).** Окремих 5-годинних бюджетів по моделях немає. Поточні смуги `opus/sonnet/haiku` з бюджетами в конфігу концептуально хибні, їх треба замінити (див. T6). Для порівняння, `get_usage` у Desktop показав 5h = 50%, weekly = 54%, а мій оцінювач показував sonnet 12%, opus 5%.
4. **statusLine отримує в JSON офіційні `rate_limits.five_hour` / `seven_day` (`used_percentage`, `resets_at`), `context_window.context_window_size`, `context_window.used_percentage`, `session_id`, `transcript_path`.** `rate_limits` є лише для Pro/Max і лише після першої відповіді API. `used_percentage` контексту рахується за входом: `input + cache_creation + cache_read`, **без** `output_tokens`. Наш поточний розрахунок додає output, тож розходиться на ~1k токенів.
5. **Реальне вікно контексту: 1 000 000, автокомпакт на 97%** (за `get_usage`). Це закриває питання з визначенням вікна, див. T7a.
6. **`textual.fuzzy.Matcher` уже є в Textual 8.2.8** (перевірено: `apirf` → `api-refactor` дає 9.52, `docs-writer` дає 0). Нова залежність не потрібна.
7. **Прапорці CLI:** `--resume <id>`, `-c/--continue`, `--fork-session`, `--session-id`, `--model`, `--permission-mode`, `--add-dir`, `-w/--worktree`. `claude` лежить у `~/.local/bin/claude`. Бінарники Desktop окремі: `~/Library/Application Support/Claude/claude-code/<ver>/…/claude --output-format stream-json`, батько — обгортка `disclaimer`.
8. `tmux` не встановлено. `it2` (iTerm2 CLI) є, але ти обрав запуск у тому ж терміналі, тож це не потрібно.

## M1

### T0 · Реєстр живих процесів з `~/.claude/sessions` · M
**Мета.** Єдине джерело правди про PID і «живе / мертве», на якому тримаються T1, T2, T4.

**Реалізовність:** ✅ формат перевірено.

**План**
- `registry.py`: читає `sessions/*.json` (каталог перевизначається `CLAUDE_SESSIONS_DIR` для тестів), повертає `LiveSession{pid, session_id, cwd, name, status, entrypoint, kind, version, started_at}`.
- Живість: `os.kill(pid, 0)` + збіг `startedAt` з часом старту процесу (`ps -o etime=` або `sysctl`/`psutil`). `psutil` не потрібен: достатньо `ps -o lstart=`/`etime=` з парсингом, але якщо код стане громіздким, додати залежність.
- `Agent` отримує `pid`, `entrypoint`, `live_status`. Прив'язка за `sessionId` (субагенти PID не мають).
- Файли мертвих процесів ігнорувати (не видаляти).
- (за результатом S2) використати `status` як сигнал `busy` / `idle` поряд із hooks.

**Критерії приймання:** для кожної з 4 живих сесій у `status --json` видно `pid` і `entrypoint`; мертві PID не показуються як живі; тест із підміненим каталогом і фіктивним процесом.
**Ризики:** формат недокументований і може змінитись → жорстка валідація полів, відсутній файл не ламає застосунок.

### T1 · Колонка PID · S
**Реалізовність:** ✅ (залежить від T0).

**План:** колонка `PID` у `DataTable` (ширина 6) між MODEL і TIME; `—` для мертвих, субагентів і сесій без файлу; ховати колонку при ширині < 100; у деталях додати `PID`, `Entrypoint` (Desktop / CLI), `Version`; PID у `status --json`; клавіша копіювання PID (`p`).
**Критерії приймання:** живі сесії мають PID, завершені мають `—`, UI не «стрибає» при появі PID.

### T5 · Нечіткий пошук (fuzzy) · S
**Реалізовність:** ✅ `textual.fuzzy.Matcher`, нових залежностей немає.

**План**
- Поле `/` тепер fuzzy: токени без `:` матчаться проти `name`, `project`, `branch`, `prompt` (з вагами: name ×3, project ×2, branch ×1.5, prompt ×1); токени `key:value` (`status:`, `model:`, `project:`) лишаються точними, як зараз.
- Результати сортуються за score (потім за urgency), у колонці AGENT підсвічується збіг (`Matcher.highlight`).
- Порожній запит повертає звичайне сортування.
- Продуктивність: < 20 мс на 500 сесій (кешувати `Matcher` на запит, рахувати лише змінений ввід).
- Помітити в довідці `?`.

**Критерії приймання:** `apirf` знаходить `api-refactor` першим; `status:waiting dep` комбінується; тести на ранжування й на комбінацію токенів.

### T2 · Гаряча клавіша kill із підтвердженням · M
**Реалізовність:** ✅ технічно просто. ⚠️ для Desktop-сесій поведінка після kill невідома (S4).

**План**
- `x` на вибраній живій сесії відкриває модальне вікно: `Kill «<name>» (pid 96635, Desktop)? [y/N]`, за замовчуванням **N**, `esc` скасовує.
- Дії: `y` → `SIGTERM`; чекати 3 с; якщо процес живий, показати `Still running — SIGKILL? [y/N]`.
- **Запобіжники** (обов'язково, тести на кожен):
  1. перед сигналом заново читати pid-файл і звіряти `startedAt` (захист від перевикористання PID);
  2. не вбивати `pid ≤ 1`, чужі UID, власний процес і **будь-якого предка TUI** (щоб не вбити сесію, з якої запущено `agents-farm`);
  3. вбивати лише `claude`-процес із pid-файлу, **не** батька (`disclaimer`/Desktop);
  4. для `entrypoint=claude-desktop` додатковий рядок у підтвердженні: «Desktop керує цим процесом; сесія може показатись у Desktop як завершена з помилкою» (текст уточнити після S4);
  5. запис дії в `~/.agents-farm/actions.log` (час, pid, ім'я, сигнал), права 0600.
- Для мертвих сесій і субагентів клавіша неактивна з поясненням.
- Опційно: окрема клавіша `i` для перериву поточного ходу (SIGINT), лише якщо S4 покаже, що це безпечно.

**Критерії приймання:** тест із породженим `sleep`-процесом і фіктивним pid-файлом (kill, неправильний `startedAt` → відмова, предок → відмова); без підтвердження сигнал не надсилається.
**Ризики:** випадково вбити робочу сесію → підтвердження за замовчуванням «N», в тексті видно ім'я й тривалість.

## M2

### T3 · Нова сесія по гарячій клавіші (CLI claude) · M
**Реалізовність:** ✅ той самий механізм, що `o` (pager): `App.suspend()` + `subprocess`. ⚠️ треба S3.

**План**
- `n` відкриває діалог: каталог (за замовчуванням `cwd` вибраної сесії; список недавніх проєктів із `~/.claude/projects` з fuzzy-вибором, T5), модель (`--model`, за замовчуванням з конфігу), режим дозволів (`--permission-mode`), чекбокс `-w` (worktree).
- Окремий `runner.py`: `run_interactive(cwd, args)` — `suspend()`, ігнорувати SIGINT у батьківському процесі на час роботи дочірнього (Ctrl-C іде в `claude`), після виходу відновити TUI й виділити нову сесію (виявляється новим pid-файлом / транскриптом, T0).
- Конфіг: `claude_bin` (за замовчуванням `claude` із PATH, інакше `~/.local/bin/claude`), `claude_args` (додаткові прапорці), `claude_env`.
- Помилки: каталог відсутній, `claude` не знайдено, код виходу ≠ 0 → сповіщення з текстом, а не падіння.
- Аргументи передавати списком (без shell), шлях і введення користувача не інтерполюються в рядок.

**Критерії приймання:** `n` → `claude` запускається в потрібному каталозі, після `/exit` TUI повертається з коректним екраном; неіснуючий каталог дає зрозумілу помилку; тест на формування аргументів (без запуску реального `claude`).
**Ризики:** відновлення стану термінала (миша, alt-screen) на різних терміналах → S3; сесія блокує TUI, поки відкрита (прийнято за вибором «у цьому ж терміналі»).

### T4 · Продовжити (resume) сесію · M
**Реалізовність:** ✅ `claude --resume <id>` у `cwd` сесії. ⚠️ конфлікт, якщо процес живий.

**План**
- `r` (і `enter` на неживій сесії) → `runner.run_interactive(cwd, ["--resume", session_id])`.
- **Перевірка живості (T0):**
  - процес мертвий → resume одразу;
  - процес живий (особливо Desktop) → діалог: «Сесія вже запущена (pid N). Відкрити **форк** (`--fork-session`, нова історія з копії) / скасувати». Повторне відкриття тієї ж сесії двома процесами не пропонуємо: обидва писали б в один транскрипт.
- Субагентські транскрипти не відновлюються (клавіша неактивна).
- `c` — `--continue` для найновішої сесії в каталозі.
- Перевіряти існування `cwd`; якщо каталог зник, показати помилку з шляхом.
- Лишити `y` (копіювати команду) для відновлення в іншому терміналі.

**Критерії приймання:** resume мертвої CLI-сесії працює; для живої Desktop-сесії пропонується форк, а не дубль; тести на логіку вибору режиму (без запуску `claude`).

## M3

### T6 · Моніторинг лімітів: справжні дані через statusLine · L
**Реалізовність:** ✅ офіційний канал є. ⚠️ чи працює для Desktop-сесій — S1. Лише Pro/Max, і лише після першої відповіді API.

**Що змінюється:** замість трьох смуг по моделях і бюджетів у конфігу — **дві смуги: 5-годинне вікно і тиждень**, з відсотком, часом до скидання й темпом.

**План**
1. **`agents-farm statusline`**: читає JSON зі stdin, атомарно пише `~/.agents-farm/state/<session_id>.json` (права 0600: `rate_limits`, `context_window`, `model`, `transcript_path`, час запису), друкує компактний рядок для самого statusLine. Підтримує ланцюжок: `--then "<існуюча команда>"` (settings дозволяє лише один `statusLine`, поточного в тебе немає).
2. **`agents-farm install-statusline`**: показує diff для `~/.claude/settings.json`, робить резервну копію, питає підтвердження, відмовляє без ланцюжка, якщо `statusLine` уже є. Без мовчазних змін.
3. **Store:** ліміти акаунта = найсвіжіший `rate_limits` серед усіх state-файлів (ліміт спільний для сесій). Показувати вік даних («станом на 3 хв тому»); прострочені (`resets_at` у минулому) позначати як невідомі.
4. **UI:** нижня панель `5h ███████░░░ 50% ↻2h42m │ 7d ██████░░░░ 54% ↻4d8h`; маркер темпу (використано % проти частки вікна, що минула) з попередженням «вичерпаєш за ~X, якщо так триватиме»; пороги warn/crit як зараз; сповіщення один раз на вікно.
5. **Fallback**, якщо даних statusLine немає (S1 негативний або не Pro/Max): стара оцінка за токенами, але без бюджетів по моделях, явно позначена `≈` і підказкою «встанови statusline для точних даних».
6. **Конфіг:** `limits` (бюджети по моделях) і `window_hours` позначити застарілими; міграція не потрібна, ключі просто ігноруються з попередженням.

**Критерії приймання:** після установки statusLine у CLI-сесії дашборд показує ті самі відсотки, що й `/usage`; Desktop-сесія — за результатом S1; тести на ланцюжок команд, атомарний запис, прострочені дані, відсутній `rate_limits`.
**Ризики:** (a) Desktop не запускає statusLine → ліміти оновлюються лише при активних CLI-сесіях (S1); (b) правка `settings.json` → резервна копія й явне підтвердження; (c) statusLine запускається часто (дебаунс 300 мс) → обробник швидкий, без імпорту Textual.

### T7 · Відсотки по сесіях (обидва показники) · M

#### T7a · Заповнення контексту
**Реалізовність:** ✅ дані вже є.
- Джерело за пріоритетом: **state-файл statusLine** (`context_window.used_percentage`, `context_window_size`) → транскрипт з вікном із конфігу.
- Виправити формулу: `input + cache_creation + cache_read` **без** `output` (збігається з офіційним значенням).
- Показувати маркер автокомпакту (~97%) і попереджати біля нього.
- Це знімає потребу в `context_window` у конфігу для сесій зі statusLine.
- Критерії: значення збігається з `/context` у межах 1%; тести для двох джерел і пріоритету.

#### T7b · Частка сесії в лімітах
**Реалізовність:** ⚠️ **офіційного розподілу по сесіях немає, лише оцінка.**
- Формула: `частка(сесії) = used_5h% × (зважені токени сесії у вікні ÷ зважені токени всіх сесій у вікні)`. Так суми по сесіях дорівнюють реальному відсотку акаунта.
- Ваги токенів (конфіг, за замовчуванням за співвідношенням цін API): input 1, output 5, cache_create 1.25, cache_read 0.1. Це допущення, його треба відкалібрувати; ліміти підписки не лінійні за токенами.
- Колонка `5H%` зі знаком `≈`; у деталях ще й `7d%`. Сортування за цією колонкою (`s`).
- Сесії без активності у вікні мають `—`.
- Критерії: сума часток ≈ відсотку акаунта; тест на розподіл; підказка в довідці, що це оцінка.

Найбільший невідомий фактор: **S1** (чи працює statusLine у Desktop-сесіях). Від нього залежить, наскільки точними будуть ліміти для твого основного сценарію, тож його варто зняти до початку T6, бажано першим.
